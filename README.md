# Система партнёрских отчислений

Набор микросервисов на **.NET 10**, **EF Core**, **PostgreSQL** и **Kafka**. Система принимает события о прибыли пользователей,
считает комиссии для цепочки партнёров над пользователем и периодически выплачивает их на внутренние кошельки.

## Как запустить

Нужен Docker. Одна команда поднимает инфраструктуру и все сервисы:

```bash
docker compose up --build
```

Миграции БД применяются при старте сервисов, топики Kafka создаёт контейнер `kafka-init`.

| Что | Адрес |
|---|---|
| **API (gateway)** | http://localhost:8080 |
| Aspire Dashboard (метрики и трейсы) | http://localhost:18888 |
| Kafka UI (топики, сообщения, dead-letter) | http://localhost:8090 |
| Сервисы напрямую | Partners `5101` (REST) и `5102` (gRPC), Commission `5201`, Wallet `5301` |

Тесты: `dotnet test`. Интеграционным тестам нужен запущенный Docker, PostgreSQL они поднимают сами через Testcontainers.

Несколько реплик Commission и Wallet запускаются так:

```bash
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale commission=3 --scale wallet=2
```

## Архитектура

### Сервисы
Четыре процесса, у каждого из первых трёх своя база PostgreSQL:

- **Partners** (`partners_db`) — пользователи и дерево партнёров, защита от циклов. Отдаёт цепочку предков по gRPC.
- **Commission** (`commissions_db`) — принимает события о прибыли, считает комиссии по схеме Linear или Fibonacci, хранит `schema_type` в каждой комиссии.
- **Wallet** (`wallets_db`) — копит начисления, периодически выплачивает их на кошельки, ведёт баланс и историю выплат.
- **Gateway** (YARP) — единая точка входа, только маршрутизирует запросы по путям.

### Как они общаются

- **Kafka** — для всего, что должно пережить сбой соседа. Три топика: `profit-events`, `commission.accrued`, `wallet.commissions-paid`. У каждого есть топик `*.dlt` для сообщений, которые не удалось обработать.
- **gRPC** — единственный синхронный вызов: Commission спрашивает у Partners цепочку партнёров.
- **REST** — внешний API для клиентов, через gateway.

### Согласованность без распределённых транзакций

- В каждом сервисе одна локальная транзакция, а отправка в Kafka идёт через **outbox**.
- Потребители идемпотентны (уникальные ключи, `ON CONFLICT DO NOTHING`, **inbox**), поэтому повторы безопасны.
- Параллельные инстансы не мешают друг другу благодаря `FOR UPDATE SKIP LOCKED`.
- Ошибки обработки делятся на постоянные (сразу в dead-letter), обычные (5 попыток) и временные (повторы без лимита).

## Комментарии

- **`ExternalId` пользователя — строка**, потому что непонятно, в каком формате он может храниться в чужой системе. Внутренние идентификаторы в рамках сервиса — `Guid`.
- **Масштабирование** работает только для частей, которые работают через Kafka: consumers, outbox и выплаты (Commission и Wallet). HTTP-запросы через gateway и gRPC-вызов идут на одну реплику, потому что балансировщика нагрузки в проекте нет.
- **Aspire Dashboard** добавлен в качестве эксперимента, для визуализации метрик.
